## The problem

There are about 33 million small businesses in the United States, and the vast
majority have no IT staff, let alone a security person. Their owners are told
constantly that they should "do something about cyber security". What they are
offered is either a $5,000 consulting engagement or a 56-item control
framework written for people who already know what a control framework is.

So most of them do nothing. Not out of negligence — out of not knowing which
of the hundred possible things to do first, and having no way to tell whether
they have done enough.

Meanwhile the pressure to demonstrate something is rising from every
direction: cyber insurers now ask about multi-factor authentication before
they will quote, larger clients send security questionnaires before they will
contract, and a ransomware event at this size is frequently terminal.

## What Baseline does

Ten minutes, 26 plain-English questions, no account, no email.

Out of it comes a readiness score out of 100, a breakdown across six areas,
and a prioritised 30-day plan: what to do, why it matters in terms of the
owner's own business, what it costs, and roughly how long it takes. Printable,
and shareable on a private link.

Every question maps to a specific safeguard in the CIS Critical Security
Controls v8, Implementation Group 1 — the baseline set of practices recommended
for small organisations. The score is therefore not a marketing number; it
corresponds to a recognised framework, and 42 distinct IG1 safeguards are
covered.

The difference from a generic checklist is the translation. Not "implement
MFA on externally-exposed enterprise applications" but "Is multi-factor
authentication turned on for email, banking, and remote access?", with a note
explaining that this means a second step after the password, usually a code
from an app on your phone.

## Architecture

![Architecture](architecture.svg)

Entirely serverless, one CDK stack in `us-east-1`:

- **CloudFront + S3** (Origin Access Control, HTTPS only) for the React app
- **API Gateway HTTP API → two Lambda functions** (Python 3.12), one per route
- **DynamoDB**, on-demand, with a 90-day TTL on every report
- **Amazon Bedrock** (Anthropic Claude Haiku-class), called only from Lambda
- **CloudWatch** dashboard, error alarm, 14-day log retention
- **AWS Budgets** alert at $20/month

The API is routed through CloudFront at `assessments*`, so the browser never
makes a cross-origin request. Full reasoning in
[`ARCHITECTURE.md`](ARCHITECTURE.md).

## What is interesting about how it is built

**The score is not generated by the model.** It is computed in Python from the
question bank, and there are tests asserting it is deterministic, independent
of JSON key ordering, and monotonic in every answer. A readiness score a
customer might show an insurer cannot be something that varies between runs.
The model writes the plan's wording; it never writes the number.

**The model cannot be prompt-injected, because it is never given free text.**
What Bedrock receives is assembled field by field: the score, the section
breakdown, the failed safeguards, the industry, and the headcount. There is no
path from a text input to the prompt, because there is no free-text input. The
optional business name and email are stored and never sent, with a test
asserting it.

**The fallback is a real product, not an error path.** Every field Bedrock
returns is validated or clamped. On any failure — timeout, throttle, malformed
JSON, wrong shape — the app builds the plan from the question bank's own
remediation copy instead, spread across four weeks by urgency. The owner gets
the same advice; only a `source` field in the response differs. The app cannot
show an error page because a model call was slow.

**It practises what it recommends.** The create Lambda holds
`dynamodb:PutItem` on one table ARN and `bedrock:InvokeModel` on one model
ARN; the read Lambda holds `dynamodb:GetItem` and nothing else. Not
`grantWriteData()`, which would also grant Update, Delete and the batch
calls. Report links carry 128 bits of entropy. The S3 bucket has no public
path. Every response carries CSP, HSTS, `X-Content-Type-Options`,
`Referrer-Policy`, and `frame-ancestors 'none'`. A security product whose own
IAM policy is `Resource: "*"` is not a serious one.

## Commercial potential

The free check is the top of the funnel; it is genuinely useful on its own,
which is what makes it spread.

- **Re-assessment and tracking** — a subscription for businesses that need to
  show improvement over time, which is exactly what insurers and enterprise
  procurement ask for.
- **The questionnaire as an artefact** — a shareable, dated report is already
  the thing a client's vendor-security review is asking for. Selling a version
  with the business's own branding is a small step.
- **Channel distribution** — the natural sellers are not us. Insurance brokers,
  MSPs, accountants and industry associations all have the relationship and a
  reason to want their clients more secure. A white-labelled Baseline is a
  lead generator for them and a distribution channel for us.
- **Upgrade path to IG2** — IG1 is the floor. Businesses that outgrow it are
  the ones who can pay.

The economics work because the marginal cost of an assessment is one small
Bedrock call and a DynamoDB write — fractions of a cent. There is no seat to
provision and nothing running between assessments.

## Honest limits

- A self-assessment is only as accurate as the answers. Baseline says so on
  the report and is designed to make honesty easy — "Not sure" is a normal
  answer, scored the same as "No", rather than something to be embarrassed by.
- It is not a certification, an audit, or legal advice, and the report says so.
- IG1 is a floor, not a finish line. A score of 100 means the basics are in
  place, which is a good place to be and not the same as being secure.
- Reports are protected by an unguessable link rather than a login. That is a
  deliberate trade — requiring an account to see a free score would lose most
  of the people this is for — and the report page states it plainly.
